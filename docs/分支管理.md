# 分支管理

本文说明「将星谱」采用的分支模型、合并策略，以及一次真实的冲突解决流程。目标是让 `main` 始终可构建、可运行、可评审，同时保留清晰的协作历史。

## 模型

采用**短生命周期功能分支 + Pull Request** 的主干开发模型：

```
main ──●────────●────────●────────●────────●──→
        \      /          \      /          \
         ●──●─              ●──●─            ●──●
     feature/a           fix/b            docs/c
```

- `main` 是唯一长期分支，受保护，不允许直接 push。
- 每个改动从最新 `main` 切出，生命周期以天计，合并后立即删除。
- 所有进入 `main` 的改动都经过 PR、CI 和至少一次评审。
- 发布以 `main` 上的提交打标签（`v0.2.0`），不另开 `release` 长期分支。

### 分支命名

| 前缀 | 用途 | 示例 |
| --- | --- | --- |
| `feature/` | 新功能 | `feature/battle-replay` |
| `fix/` | 缺陷修复 | `fix/codex-search-empty` |
| `docs/` | 文档 | `docs/branching` |
| `refactor/` | 行为不变的重构 | `refactor/core-events` |
| `chore/` | 构建、依赖、CI | `chore/node-24` |

分支名使用小写英文与连字符；一个分支只解决一个问题。

## 日常流程

```bash
# 1. 同步主干
git switch main
git pull --ff-only

# 2. 切出功能分支
git switch -c feature/battle-replay

# 3. 开发并小步提交
git add src/core/battle.ts tests/battle.test.ts
git commit -m "feat(battle): 记录逐回合事件流"

# 4. 推送并创建 PR
git push -u origin feature/battle-replay

# 5. CI 通过、评审通过后，在 GitHub 选择 Create a merge commit
# 6. 删除远程与本地分支
git switch main
git pull --ff-only
git branch -d feature/battle-replay
```

## 合并策略

统一使用 **merge commit**（`--no-ff`），原因：

1. 保留「这个功能是在哪个分支、哪次 PR 里完成的」这一层信息；
2. 出现回归时可以整体回滚一个 merge commit；
3. 冲突解决的过程本身留在历史里，便于复盘；
4. 与 GitHub 的 PR 记录一一对应，评审链接不会丢。

不采用 squash：会把一个功能的多个逻辑提交压成一条，丢失「先加测试、再改实现、最后修边界」的过程。也不在共享分支上 rebase，避免重写他人已经拉取的历史。

## 保护规则

`main` 分支启用以下规则（GitHub Ruleset / Branch protection）：

- 禁止直接 push 与强制 push
- 合并前必须通过 CI（类型检查、测试、构建）
- 至少 1 位评审者 Approve
- 合并后自动删除源分支
- 要求分支与 `main` 保持最新（Require branches to be up to date）

## 冲突解决

冲突不是错误，而是两条分支对同一处文本做了不同修改。处理原则：**理解双方意图，保留两者都需要的部分，必要时重构，而不是简单选一边。**

### 1. 同步主干

```bash
git fetch origin
git switch feature/battle-replay
git merge origin/main
```

### 2. 定位冲突

```bash
git status
# both modified: README.md
```

冲突文件中会出现标记：

```text
<<<<<<< HEAD
当前分支的内容
=======
origin/main 的内容
>>>>>>> origin/main
```

### 3. 手工合并

打开文件，保留双方的有效内容，删除三行标记。常见做法：

- 两边都在路线图末尾新增条目：两条都保留，按优先级排序。
- 一边改文案、一边改结构：把文案放进新结构。
- 两边改同一段逻辑：先写一个能同时满足两边测试的实现，再删旧代码。

### 4. 验证并提交

```bash
npm run typecheck
npm test
git add README.md
git commit            # 生成 merge commit
git push
```

PR 会自动更新为可合并状态，CI 重新运行。

### 5. 不要做的事

- 不要用 `git checkout --ours` / `--theirs` 静默丢弃一边。
- 不要为了「看起来干净」删除对方的提交。
- 不要在冲突未解决时 force push 覆盖远程分支。
- 不确定时在 PR 中说明两边意图，邀请维护者一起看。

## 本仓库的实践记录

| 分支 | 内容 | 结果 |
| --- | --- | --- |
| `feature/community-docs` | 贡献指南、行为准则、Issue/PR 模板、CI、架构与战略文档 | PR 合并 |
| `feature/roadmap-multiplayer` | 路线图新增「联机对战」规划 | PR 合并 |
| `feature/roadmap-ranked` | 路线图新增「赛季排位」规划 | 与上一条在 README 同一位置冲突，手工合并后合并 |

两条路线图分支都在「路线图」列表末尾追加内容，先合并的分支占用了同一位置，后合并的分支因此产生冲突。解决时保留两条规划，并按「先联机、后赛季」的产品顺序排列，随后重新运行类型检查与 45 项单元测试。

## 版本与发布

- 版本号遵循语义化版本：`0.x` 阶段允许小版本引入破坏性变更，但需在 `CHANGELOG.md` 的「变更」中注明。
- 发布步骤：更新 `CHANGELOG.md` → 合并 PR → 在 `main` 上打标签 → 推送标签 → 创建 GitHub Release。
- 标签使用 `v` 前缀，例如 `v0.2.0`；Release Notes 直接引用 `CHANGELOG.md` 对应段落。
