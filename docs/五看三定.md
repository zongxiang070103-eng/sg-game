# 将星谱：五看三定分析

> 分析对象：开源项目「将星谱 · 三国卡牌演武」（3v3 明牌回合制卡牌战棋，MIT 许可）。
> 方法：华为「五看三定」——先看行业/趋势、市场/客户、竞争、自己、机会，再定战略控制点、目标、策略。
> 说明：本文以项目自身数据、公开行业信息与课程场景为依据；涉及市场规模的判断为方向性估计，不作为精确预测。

## 一、五看

### 1. 看行业与趋势

**游戏行业进入存量竞争，独立与开源游戏反而获得结构性空间。** 头部商业手游依赖买量、抽卡与长线运营，研发与发行成本高企；与此同时，Steam、itch.io、GitHub 上的独立游戏与开源游戏凭借差异化玩法、低门槛分发和社区口碑持续出现。开源游戏并不新鲜：`0 A.D.`、`Battle for Wesnoth`、`SuperTuxKart` 都证明了「开源 + 社区内容」可以长期存活，只是商业化路径与商业游戏不同。

**技术趋势有三条与本项目直接相关：**

1. **Web 技术跨端化。** TypeScript + Vite + Capacitor 让一套代码同时跑在浏览器、PWA 和安卓壳里，独立开发者不必为每个平台重写。
2. **数据驱动与可验证性。** 把武将、技能、数值放进 JSON，把规则核心与 DOM 解耦，就能在 Node 里批量模拟、回归测试和平衡分析。这正好契合「开源可审计」的文化。
3. **AI 辅助生产。** AI 能降低美术、文案、测试的边际成本，但也带来素材授权、同质化和「看起来差不多」的风险。开源项目必须把授权与来源写清楚，否则会反噬信誉。

**政策与平台环境。** 国内商业卡牌游戏受版号、防沉迷、抽卡概率公示等约束；非商业开源项目不涉及发行，但仍需注意素材版权、历史人物形象与内容合规。GitHub 的 Actions、Pages、Issues、Discussions 为教学与社区协作提供了免费基础设施。

**趋势判断：** 大众卡牌市场拥挤，但「规则透明、无随机、可复盘、可二次开发」的轻量策略游戏仍有细分空间；开源与教学场景是低成本获客与建立口碑的入口。

### 2. 看市场与客户

把潜在用户分成四层：

| 用户 | 核心诉求 | 本项目能提供 | 触达方式 |
| --- | --- | --- | --- |
| 三国 / 卡牌 / 战棋核心玩家 | 策略深度、公平、可复盘、不逼氪 | 明牌无随机、3v3 换将、战报、离线 | 游戏社区、B 站、贴吧、GitHub |
| 独立开发者与学生 | 可读可改的完整案例、工程实践 | TypeScript 全栈、测试、QA、CI、文档 | GitHub、课程、技术文章 |
| 开源文化 / 软件工程课程 | 可演示的分支、PR、Issue、冲突、CI | 真实提交历史与协作记录 | 课堂、实验手册 |
| 移动端轻度玩家 | 碎片时间、低配置、免安装 | 单页离线、PWA / APK | 分享链接、应用包 |

**需求侧的关键判断：**

- 核心玩家对「抽卡 + 数值膨胀」疲劳，愿意为公平、可复盘的策略体验付出时间，但对付费谨慎。
- 开发者需要的不是又一个商业游戏，而是**能跑、能读、能改、文档齐**的样本；这类需求在课程与求职场景中更刚性。
- 课程场景需要真实的分支冲突、Issue 讨论和 CI 记录，恰好可以由本仓库持续提供。

**市场规模与验证。** 本项目不追逐大众 DAU，而以「细分社区 + 教学场景」为目标。验证指标不是收入，而是 star、fork、issue 质量、外部 PR、课程使用反馈。当前项目处于 MVP 阶段，尚未做系统用户调研，这是后续要补的功课。

### 3. 看竞争

**直接竞争：**

- **《三国杀》等国民卡牌**：IP 强、社交强、商业化成熟；劣势是规则复杂化、付费点多，且并非开源。
- **《率土之滨》等 SLG**：长线运营、重社交、重付费；与本项目的轻量单机定位不在同一战场。
- **《月圆之夜》《杀戮尖塔》等单机卡牌**：品质高、买断制；但偏 PvE roguelike，缺少 3v3 明牌对战与开源属性。
- **开源战棋（Battle for Wesnoth、0 A.D. 等）**：社区成熟、内容量大；但多为 PC 端、上手门槛高、技术栈偏传统。

**间接竞争：** 通用卡牌框架、游戏引擎模板、各类「开源学习项目」都在争夺开发者的注意力。

**差异化对比：**

| 维度 | 商业卡牌 | 单机卡牌 | 开源战棋 | 将星谱 |
| --- | --- | --- | --- | --- |
| 规则透明 | 部分 | 部分 | 高 | 高（源码 + 文档） |
| 随机性 | 抽卡/发牌 | 高 | 中 | 无随机，可复盘 |
| 3v3 换将 | 少 | 少 | 少 | 有 |
| 开源可改 | 否 | 否 | 是 | 是（MIT） |
| 跨端离线 | 否 | 部分 | 部分 | Web / PWA / APK |
| 美术与 IP | 强 | 强 | 中 | 弱（待原创替换） |
| 社区规模 | 大 | 中 | 中 | 小（起步） |

**竞争结论：** 不与商业产品拼美术、IP 和买量；以「开放规则 + 可验证平衡 + 低门槛二次开发」错位竞争。最大的短板是美术授权与社区冷启动，最大的长板是工程完整度与可复盘性。

### 4. 看自己

**资源与能力：**

- 1 名维护者，借助 AI 辅助完成规则、界面、测试、文档与美术处理。
- 60 名武将、180 个主动战法、60 个天赋，全部由 JSON 驱动。
- 核心规则约 2,182 行 TypeScript，45 项单元测试，10 张无头浏览器 QA 截图，300 局 AI 模拟。
- 完整闭环：点将台 → 布阵 → 战场 → 战报 → 结算；可离线运行。
- MIT 许可、README、贡献指南、行为准则、安全策略、Issue/PR 模板、CI。

**优势：**

1. 规则核心不依赖 DOM，可测试、可模拟、可复用。
2. 数据与代码分离，新增内容成本低。
3. 无随机数，输赢可复盘，适合做平衡分析与教学案例。
4. 单页离线，部署和评审成本极低。
5. 文档与自动化程度在同类学生项目中偏高。

**劣势：**

1. **美术资源授权待确认**：当前场景立绘为 AI 生成资源包，公开再分发前必须确认条款或替换为原创/CC0 素材。
2. **单人维护的 bus factor**：维护者离开后项目可能停摆，需要 co-maintainer 与文档化。
3. **无联机、无云存档**：社交传播弱，长期留存有限。
4. **移动端与无障碍**：虽有两档断点与键盘操作，但触控手感、读屏支持仍需打磨。
5. **社区运营零基础**：没有稳定的内容节奏与用户反馈渠道。

**自我判断：** 项目已经越过「能不能玩」的门槛，处于「可演示、可教学、可二次开发」的 MVP 阶段；距离「可持续的开源社区项目」还差素材合规、联机/回放、社区运营三块。

### 5. 看机会

- **教学与课程场景**：开源文化、软件工程、Web 开发课程都需要真实仓库做分支、PR、Issue、冲突与 CI 演示。本项目的提交历史可以直接作为案例。
- **开发者社区**：Hacktoberfest、开源之夏、Game Jam、校内社团；用 `good first issue` 把文档、测试、数据校对拆成可认领任务。
- **AI 与工具链**：用 AI 批量跑平衡、生成战报解说、辅助武将文案；把「模拟 + 复盘」做成可复用的规则引擎。
- **内容二创**：三国历史与演义是公共领域，可做武将设计征集、剧本编辑器、MOD 生态。
- **轻商业化（谨慎）**：赞助、爱发电、原创皮肤、定制开发；不做抽卡与数值付费，避免破坏公平定位。

**风险：** 素材版权、同质化、社区冷启动、单人精力、范围蔓延、平台政策变化。

## 二、三定

### 1. 定战略控制点

战略控制点是「别人难以短期复制、且能随时间积累」的资产。候选有四个：

1. 60 武将 / 180 战法的规则与数值数据；
2. 可复现的平衡模拟与 QA 工具链；
3. 完整的开源工程体系（文档、测试、CI、协作流程）；
4. 中文三国策略内容的社区与教学场景。

**选择：以「开放规则 + 可验证平衡 + 低门槛二次开发」三位一体作为控制点。** 不以美术或 IP 为控制点——那需要持续高投入，且与商业团队正面竞争。护城河来自：数据与工具链的开源生态、贡献者网络、以及被课程与教学反复引用的案例地位。

**明确不做：** 抽卡付费、重美术军备竞赛、短期重运营联机、需要版号的商业发行。

### 2. 定目标

**愿景：** 成为中文开源战棋/卡牌领域「规则透明、可复盘、可教学」的代表性项目。

**分阶段目标：**

| 阶段 | 时间 | 目标 | 验收指标 |
| --- | --- | --- | --- |
| 课程交付 | 0–1 个月 | 仓库达到开源项目基本标准 | LICENSE / README / 文档 / CI / 分支 / Issue 完整；10+ star；3+ issue；1+ 外部贡献者 |
| 可用性 | 1–3 个月 | 移动端与复盘体验补齐 | PWA 可安装；战报回放；30+ star；3+ contributors；测试 60+ |
| 社区化 | 3–6 个月 | 形成稳定的贡献与内容节奏 | 100+ star；10+ contributors；每月平衡报告；联机原型 |
| 长期 | 6–12 个月 | 成为可复用的规则引擎与教学样本 | 1.0 版本；2 篇技术文章；课程/社团采用；素材 100% 合规 |

**非目标：** 收入、DAU、商业发行、与头部产品比美术。

### 3. 定策略

**产品策略：** 先把单机做深——战报回放、难度分级、编队预设、剧本编辑器；再做轻量联机（房间码 + 回合同步）。移动端优先 PWA，APK 作为补充。

**技术策略：** 核心层保持无 DOM、可测试；数据驱动扩展；CI 门禁（typecheck / test / build）；语义化版本与 CHANGELOG；性能预算与包体控制。

**社区策略：**

- 文档先行：CONTRIBUTING、行为准则、Issue/PR 模板、架构说明、分支管理。
- `good first issue`：文档校对、数据校对、移动端样式、测试补充。
- 响应承诺：Issue 48 小时内回复，PR 7 天内给出评审意见。
- 每月发布一次平衡报告，公开模拟数据与调整理由。

**内容与合规策略：** 制定素材授权清单；优先替换为原创或 CC0 美术；所有第三方资源在 `SOURCE.md` 登记；发布前做许可证审计。

**教学策略：** 把仓库作为课程案例，提供分支演练、冲突复现、Issue 讨论与 CI 观察的实验手册；用真实提交历史讲开源协作。

**资源策略：** 单人 + AI 辅助，每周固定维护窗口；优先高杠杆任务（文档、自动化、素材合规），把可外包的任务拆成 Issue。

## 三、落地路线图

| 时间 | 关键动作 | 交付物 |
| --- | --- | --- |
| 第 1 月 | 完成开源文档、CI、分支保护、Issue 模板；发布 v0.2.0 | 仓库首页、许可证、贡献指南、CI 绿灯 |
| 第 2–3 月 | PWA、战报回放、移动端手感；招募 1–2 名 co-maintainer | 可安装 PWA、回放功能、贡献者名单 |
| 第 4–6 月 | 剧本编辑器、联机原型、社区武将设计活动 | 编辑器 demo、联机房间、活动复盘 |
| 第 7–12 月 | 稳定 1.0、教学手册、技术文章、素材合规审计 | 1.0 Release、课程包、审计报告 |

## 四、风险与对策

| 风险 | 影响 | 对策 |
| --- | --- | --- |
| 美术素材授权不清 | 公开仓库被投诉/下架，损害课程评分 | 建立素材清单；未确认的素材不上传；优先原创/CC0；发布前审计 |
| 单人维护 | 项目停摆、Issue 积压 | 文档化、自动化、招募 co-maintainer、设定响应上限 |
| 社区冷启动 | 长期无人 star/issue | 课程与社团切入、Game Jam、技术文章、good first issue |
| 范围蔓延 | 功能做不完、质量下降 | 路线图与非目标、双周迭代、每个版本只做三件事 |
| 同质化 | 被更容易上手的项目替代 | 强化无随机/复盘/开放规则，做深「可验证平衡」 |
| 安全与依赖 | 账号服务漏洞、供应链风险 | SECURITY.md、依赖锁定、CI 审计、最小权限 |

## 五、结论

**五看结论：** 行业增量在独立/开源与跨端轻量产品；目标客户是核心策略玩家、开发者与课程场景；竞争激烈但「开放规则 + 可复盘 + 可二次开发」的定位清晰；自身工程完整、素材与社区是短板；机会集中在教学、开发者社区与 AI 工具链。

**三定结论：** 战略控制点是开放规则与可验证的工具链，而非美术或 IP；目标是分阶段成为中文开源战棋/卡牌的教学与规则样本；策略是文档先行、社区驱动、合规优先、单机做深后再联机。

**对课程作业的意义：** 本项目用真实仓库完整走了一遍开源协作流程——许可证选择、README 与文档、分支创建与合并、冲突解决、Issue 讨论、star/watch、CI 与版本发布。五看三定不是纸面分析，而是对这套协作方式可持续性的检验：只有把规则、文档、工具链和社区都做成可积累的资产，项目才不只是「交一次作业」。
